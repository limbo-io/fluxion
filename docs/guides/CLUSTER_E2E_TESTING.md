# 集群端到端回归测试方案

## 目标与边界

开发完成后，通过一个命令选择场景并验证当前代码的真实调度链路：通过 Server API 创建、发布、启用 Trigger，由 Broker 自动定时触发，产生 Execution 和 Job，经真实网络派发至 Worker，执行并上报，最终自动判定结果。

复用 fluxion-test 和 JUnit，以测试方法定义场景，通过 Maven 提供单场景、场景组与完整回归集的选择入口。本文记录已确认的方案，不代表这些能力已经实现。

领域预期以根目录 CONTEXT.md 为依据。端到端测试补充现有组件和数据库集成测试，不替代它们。

## 环境

- 每个活动场景使用隔离的 2 个 Broker、2 个 Worker 和 MySQL 测试环境。
- Broker 与 Worker 使用本地独立 Java 进程，MySQL 使用 Podman 启动。
- 所有节点运行当前代码；端口、节点身份、数据库与产物目录隔离。
- 任务准备及配置变更通过 Server 对外 API 完成；数据库用于只读观测、断言和诊断采集，不直接插入或修改调度业务数据。
- 自动检查就绪条件，自动启停节点并清理测试环境。诊断产物在清理前归档并保留。
- 并行场景各用独立环境，限制并发数；具体默认值待容量验证。

## 场景范围

以下所有场景组纳入第一版；表中编号是稳定的场景组编号，具体用例和变体已在用例目录中展开。

用例目录保留 SCH-001 正常调度与 WRK-001 Worker 故障恢复的详细样板，其余用例按同一共同契约列出准备、动作、断言及受阻原因。

| 编号 | 场景组 | 必须覆盖 |
| --- | --- | --- |
| SCH | 正常调度 | CRON、FIXED_RATE、FIXED_DELAY 真实定时触发及后续触发推进 |
| EXE | 执行链路 | 单 Executor、Workflow 串行、并行及汇合 |
| MOD | 执行模式 | STANDALONE 正常执行、失败重试、超时与节点恢复；BROADCAST 符合条件节点参与及整体结果收敛；MAP 子任务拆分、分发、完成判定及子任务失败和节点退出；MAP_REDUCE 子任务结果完整后聚合、聚合结果及 Reduce 失败处理 |
| WFL | Workflow 节点失败策略 | 节点重试耗尽后停止；启用 continueOnFailure 后失败 Job 保持 FAILED、下游继续推进，Execution 仅在满足 Workflow 结束条件后成功，并行分支不得提前结束整个 Execution |
| RET | 执行失败 | 失败后重试成功、重试耗尽、执行超时 |
| LATE | 超时后的迟到结果 | 受控阻塞 Executor 超过 Job 运行超时，按配置重试成功或重试耗尽后释放旧执行，验证旧 attempt 的迟到上报不能覆盖当前状态 |
| BRK | Broker 故障 | Execution 持久化且未创建 Job；Job 提交后未派发；Worker 执行期间，强制退出对应 Broker |
| WRK | Worker 故障 | Worker 已开始执行但未上报结果时强制退出，验证存活节点按配置恢复 |
| REJ | 故障节点重新加入 | 分别强制退出并重启 Broker、Worker，先验证存活节点接管，再验证重启节点恢复注册并参与后续任务，旧状态不造成重复创建或错误推进 |
| BND | 调度边界 | Trigger 禁用、配置发布、遗漏触发恢复、激活截止时间过期 |
| VER | 配置发布切点 | 发布时尚未创建首个 Job 的 PENDING、CLAIMED 实例置为 INVALID，按新配置重新生成；已创建首个 Job 的实例继续旧快照。覆盖发布与 Job 创建并发，核对记录版本及实际执行配置，不测试 Executor 实现对配置的兼容性 |
| ENA | Trigger 启用校验 | 首批 Job 启动前检查当前启用状态；禁用时不启动，触发前重新启用则正常启动。Workflow 或 Map/Reduce 已启动后禁用 Trigger，后续节点、阶段或子任务继续执行，不再次校验启用状态 |

每个用例明确前置条件、输入及策略配置、到达目标阶段的证据、故障动作、结果断言、过程约束、超时和清理步骤。不仅检查最终成功或失败，也检查 Execution 身份、Job 身份、重试次数、版本与结果 fencing 等该场景相关约束。

Job 为至少一次派发，不能将业务执行次数恰好一次作为框架通用保证。不同容错配置可能产生不同终态，断言须按场景配置定义。

四种执行模式按各自风险选择用例，不穷举执行模式、调度类型、故障阶段和 Workflow 的全部组合。Workflow 重点覆盖编排、失败策略及版本快照。

### 任务类型与配置矩阵

| 任务类型或编排 | 配置与输入 | 场景预期 |
| --- | --- | --- |
| STANDALONE | 正常执行 | 由符合条件的 Worker 执行，结果上报后状态收敛 |
| STANDALONE | 配置重试，先失败后成功或持续失败 | 按次数和间隔重试，分别成功或重试耗尽失败 |
| STANDALONE | 运行超时、旧 attempt 迟到上报 | 按配置恢复，旧结果不得覆盖当前状态 |
| BROADCAST | 不关注执行成败 | 等待全部目标执行完成并返回结果后整体成功，即使全部业务失败；接受确认不能代替完成结果 |
| BROADCAST | 关注执行结果，全部成功或部分失败 | 等待全部目标结果，全部成功才成功，有失败则整体失败 |
| MAP | 多个分片，全部成功或部分失败 | 检查分片集合、实际分发、结果收敛；节点异常依据 Job 节点容错配置检查恢复范围、重试次数及终态 |
| MAP_REDUCE | 全部分片成功 | 子任务结果完整后进入 Reduce，核对聚合输入和业务聚合结果 |
| MAP_REDUCE | 分片失败或 Reduce 失败 | 分别记录失败阶段，按场景配置检查重试与终态，不将聚合未完成判为成功 |
| Workflow | 节点失败，continueOnFailure 关闭或开启 | 分别停止或推进下游，保留失败 Job 的真实状态并检查汇合结束条件 |

未显式配置广播模式时，默认关注执行成败，要求全部目标执行成功。两种广播模式下，没有可用 Worker 或持续缺少执行完成反馈均按 Job 节点容错配置重试，耗尽后失败；不关注执行成败不意味着允许反馈缺失。

广播两种完成判定模式是已确认的领域需求，不代表当前配置已实现。检查 ExecutorConfig、DispatchOption、ExecutorJobConfig 和 Worker Job 后，尚未找到对应的显式配置；BroadcastJobTracker 的部分成功逻辑也不能直接作为这两种模式的预期。该差异需要单独跟进，不将缺失模式从报告中静默排除，也不以现有行为替代已确认需求。

## 故障控制与时间

进程强制退出是必测内容。先确认目标阶段已命中，再杀死对应测试进程，不用随机杀进程替代确定性场景。

允许测试专用暂停点，以命中短暂故障窗口。优先在测试代码中实现；确需触及生产代码时保持最小改动，正常启动不启用。暂停点不得移动被验证的事务边界，例如“Job 持久化后未派发”必须在事务提交后命中。

日常回归缩短可配置的心跳、租约及扫描间隔，仍走真实故障发现和恢复机制；不得直接调用接管服务来代替恢复链路。上线前用生产默认时间参数运行回归。超时按配置推导并保留机器负载余量，具体预算待测量。

## 执行模式

- 串行：首个场景失败后停止；报告保留已执行结果，所有剩余选中场景标记为未执行并说明原因。
- 并行：场景隔离，一个场景失败不影响其他场景；汇总所有结果。无法建立环境的场景也必须记录错误，不得静默遗漏。
- 任一场景失败或运行基础设施错误，命令返回失败；退出码不替代报告。
- 已知能力缺口用例标为 BLOCKED，不能静默跳过；串行首个 BLOCKED 也停止，后续 NOT_RUN，并行继续其他场景。完整门禁不允许以 BLOCKED 或未执行冒充通过。
- 不通过自动重跑成功覆盖首次失败。

## 报表和诊断产物

每次运行独立归档 HTML 明细报表、JSON 和 JUnit XML。HTML 便于人工分析，JSON 用于后续汇总，JUnit XML 用于 CI 接入。

每个选中场景及具体变体必须有结果记录，包括稳定编号、名称、状态（PASS、FAIL、ERROR、TIMEOUT、BLOCKED、NOT_RUN）、耗时、预期与实际结果、失败阶段、断言差异和诊断文件路径。运行信息记录代码版本、工作区修改状态、时间参数模式与执行模式。状态及 JUnit 映射以实现与验收约定为准。

保留各节点日志。失败时保存场景相关 Trigger、Schedule、Execution、Job、失败记录、配置版本、节点、Bucket 和租约记录，以及必要的 Worker 本地 Task 快照；超时失败额外采集存活进程线程栈，并记录采集失败原因。报告关联诊断文件，避免整库导出，不保存数据库连接凭据。成功场景保留摘要和日志。

暂不建设在线报表平台，暂未约定自动删除产物的期限。

## 发现既有缺陷时

以领域约定形成初始预期。实现与文档冲突时保留失败及证据，单独确认修实现还是修预期；不降低断言来获得全绿，也不在搭建测试时顺手修改容错逻辑。

## 实现顺序与验证点

1. 核对 API 请求、节点启动配置、可配置时间参数与阶段观测入口，明确每个用例的预期。
2. 跑通单 Executor 的真实定时触发：验证自动准备、网络执行、上报、断言、报告及清理。
3. 跑通一个指定阶段的节点强制退出场景：验证阶段证据和存活节点恢复。
4. 补齐所有场景组，再实现串行失败停止与并行环境隔离。
5. 验证测试工具本身：人为制造断言失败、启动失败和超时，检查报告覆盖所有选中场景、退出码与诊断保留行为。
6. 使用生产默认时间参数运行完整回归，测量耗时及并行资源开销。
